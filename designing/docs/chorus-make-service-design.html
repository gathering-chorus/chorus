2. What it writes

One dagu workflow file per pipeline (v2). Each operation is its own dagu step, named from the graph, grouped under its PipelineStep. A header says it is generated from the graph and must not be edited. werk.yml (act) stays as v1, by hand, untouched.

PipelineStepOperations, in order (from today's 20 act steps)
commitcommit, push
buildbuild
testtest, review
demodeploy-werk, env-up, demo-fitness, prove-live, demo — then Jeff's go (dagu human.task)
landmerge, sync, deploy-canonical, accept, crawl-delta
run frame (added by chorus-make, not modelled as steps)shared-trace, proven-round, outcome, witness-close, witness-failed

The card is the carrier (Jeff 14:55 on #4470, "this is pretty clean"): every generated workflow takes one parameter, the card. athena(card) leaves card.model_sha when the card touches the model; werk(card) appends a round {n, sha, targets}; borg(card) proves the latest round and leaves card.verdict, or routes the failure to the owning stream's step. The werk v2 workflow chorus-make writes today already runs on ${CARD}; the round record is what it adds.

Sequencing between pipelines (Jeff 2026-10-09: "i think my go is in the right place"). The go stays after Proving has staged and readied the round and before the land, so werk runs in two stretches around it. One parent dagu run per card:

athena(card)              # skipped when the card does not touch the model
werk(card) commit…demo    # appends round {n, sha, targets}
borg(card) verify, stage, ready, go
werk(card) land           # merges and deploys the round that was proven
borg(card) verify in prod, record

Each call reads the card and writes back only its own part. A failure stops the parent at that call, and the retry starts from that call.

3. The runner: dagu

Trial 2026-10-09 10:43, dagu 2.18.2, isolated home: a real verb ran; a failed step resumed with dagu retry --step --downstream without rerunning the steps before it; the go waited as a human.task with no process held; dagu human-task complete resumed it and land ran. What act needed three home-built pieces for (a second run for the go, the run pin for resume, log regexes for phase) dagu does itself.

State transitions are dagu's, not ours (Jeff 2026-10-09: "can dagu handle state transitions so we dont have to?" — yes). A run's state (queued, running, waiting on go, failed, succeeded) is dagu's own record, so the run pins in ~/.chorus/werk-runs and their reconcile-on-poll retire in v2, and /cws reads dagu status. Card moves (WIP → Done) are generated steps that call the cards verb at the step they belong to, so no one moves a card by hand and a failed step leaves the card where it was.

Open: the scheduler under launchd (Silas's lane); auth mode for loopback; how a step's events reach the spine (dagu has no per-step hook, so verbs keep writing their own).

5. Inline logic moves into verbs first

werk.yml carries about 500 lines of inline bash (proven-round 108, demo 75, prove-live 74, test 52, deploy-canonical 49, outcome 49). An operation the graph names must be a verb call, so each block becomes a verb mode before chorus-make can generate it. #4474's no-dependency card finds which blocks are actually needed first.

6. The drift check

Regenerate and diff, in pre-commit and in the pipeline; fails on any difference. Negative proof: a hand-edited step goes red. Same graph in, byte-identical file out.
