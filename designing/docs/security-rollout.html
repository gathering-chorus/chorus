Security — Rollout Map #3809

Silas · 2026-08-10 · live score: /security.html · truth as of the dates on each claim

The bar (Jeff, 2026-08-10): “the security piece must work properly on our UIs, APIs, CLIs and not be a house of cards.” This page is the standing answer to “where are we” — what the architecture is, what is solid, what is a stilt, and in what order the stilts become structure.

The architecture in three sentences

Every actor — Jeff, the three roles, services, workers, test identities — is a Principal in one security graph (urn:chorus:domains:security), with one identity provider (id.lightlifeurbangardens.com, CSS/Solid-OIDC) proving who anyone is (ADR-052). Proving who you are grants nothing: each door decides reach separately — the share-guard for public pages, the app for llug.com, the Clearing, the API envelope (ADR-054: authN is the security domain, authZ belongs to each door). Since 2026-08-10 the system measures itself against this model nightly and publishes the score at /security.html.

The five properties that make it not a house of cards

  1. One identity mechanism on every surface. No parallel logins, no bespoke tokens.
  2. No self-declared identity anywhere. A header or env var saying who you are is a claim, not a credential.
  3. Fail closed, and every refusal names its own state. “Not you”, “not shared”, “not found”, “could not measure” are different answers and must stay different (the quintet's sixth property; four instances of this defect class fixed 2026-08-09/10).
  4. Conformance machine-measured nightly. Drift surfaces as a score drop on a page, not as an incident (fitness rows + write-snapshot, #3765/#3798/#3806).
  5. Reproducible from source. A fresh store load reproduces the whole identity substrate (#3726, MODEL_SET/SECURITY_SET).

Gaps, in the order to close them

  1. Self-declared identity dies — CLIs and werk verbs present the role's real token; the doors that merge to main verify it. Kills the weakest leg. (Property 2)
  2. The envelope covers the LAN — internal APIs move behind the same door, DEC-093's “no auth on 3340” retired deliberately, with service creds and sane TTL re-minting so it does not break the pipelines that already struggle with it. (Property 1)
  3. One authorization model, four projections — today four independent allow-lists (guard file, app users.ttl, Clearing graph, envelope graph); adding or revoking a person is four edits, and only fitness row 6 keeps them from drifting. The graph becomes the source; the doors project from it.
  4. The model's empty classes get instances — Permission (~30 real rules, 0 modeled), Credential (live creds, 0 modeled), AuthBoundary (4+, 0), SecurityProbe (8, 0). This is the model-conformance half of the original fitness ask (#3765), still unbuilt.
  5. The three lying gates — pair_gate, inject_force, quality_gate document “blocking” and return allow. Verify or strip the claim. (Named 2026-08-06, unverified.)
  6. Credentials into the backup tier — ~/.chorus/identity, secrets, tunnel cred: irreplaceable, ~1.5G with the rest of tier 1, currently zero copies (#3799).
  7. Edge-policy honesty — password change from a phone fails because the tunnel blocks the account API by design, and the error says “try again”; Buzz keys are not yet derived credentials (#3674 bar).

What done means

All five properties hold on all three surfaces, and the fitness page proves it nightly: every row green, including rows that do not exist yet (CLI-identity and LAN-envelope conformance become rows when their work lands). At that point this page stops being a map of stilts and becomes the record of a structure.
