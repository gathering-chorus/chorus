Spine — Service Design

2026-09-01 — Wren (#4044). Origin: Jeff, this morning — "mcp is ~ spine at its core tho all products are visible via it" — followed by "do we have a spine service design". We did not. Thirty-five service designs existed and none of them was the thing every other one writes to. This is that doc.

Source of truth. This doc narrates structure, contracts, reach, and intent. It duplicates no field definitions.
  • designing/schemas/spine-events.json — the canonical registry: 345 event types, each with its vertebra, join keys, and field definitions.
  • ~/.chorus/chorus.log — the log itself. Append-only, never rotated (DEC, Jeff, 2026-07-23).
  • logs-service-design.html — the writer's contract (adapters, envelope, trace lifecycle). This doc owns everything downstream of the write.
Designed target state. The spine is the single append-only record of everything the team does, and it is reachable. Four guarantees: (1) one log — every emitter, in every language, appends to one file; there is no second spine; (2) one registry — an event that is not in spine-events.json cannot be written, so the registry enumerates what the system can do; (3) unbounded retention, bounded-by-query reach — the file is never rotated, and readers ask for a time range that the substrate can actually serve, rather than silently receiving whatever fits in a fixed byte tail; (4) the spine and MCP are one surface seen from two sides — MCP is the door an action goes through, the spine is the record that it happened, and neither list is authored independently of the other.

First: the word means two things

Chorus uses "spine" for two unrelated structures, and both have docs in the catalog. Any conversation about the spine should say which one it means.

Contracts

The envelope

Every line is one JSON object. The registry declares ten envelope fields — timestamp, level, appName, component, event, role, product, domain, value_stream, value_stream_step — and each event adds its own. Two further fields are the join keys that make the log a causal record rather than a pile:

  • trace — transaction scope. One filter returns an entire flow: the werk run, its hook decisions, its deploy, its demo.
  • card_id — work scope. Threads every event produced in service of one card, across roles and days.

The registry is the enumeration

Each of the 345 entries declares a vertebra (which stage of the value stream the event belongs to), its join keys, a prose description, and per-field meanings. This is what makes the registry more than validation: it is the list of things the system is able to do, in the system's own words. That property is the basis of the MCP relationship below, and it is why an unregistered emit is a defect rather than a warning.

Retention — never rotate

Jeff's ruling (2026-07-23, after a rotation destroyed reach): the spine is a memory layer, not an operational log. It is never rotated and never truncated. Disk is cheaper than a lost month. The file currently holds 1.71 GB / 2,097,133 events back to 2026-07-23 — the date of the rotation that prompted the ruling.

Reach — the gap between retained and readable

Retention is honoured. Reach is not. Every chorus-api spine reader calls readFileTail(chorus.log, SPINE_TAIL_BYTES) with SPINE_TAIL_BYTES = 4 MB (platform/api/src/server.ts:1115). Measured on the live log at 2026-09-01 07:05:

Proportion of the record reachable~0.25%
Gap 1 — the range tabs are decoration. /api/loom-metrics backs the Team Pulse 7d / 30d / 90d / All buttons and reads the same 4 MB tail. Every one of those buttons returns the same ~3 hours. The page is honest about what it fetched, but the control implies a window the substrate cannot serve.
Gap 2 — "never rotate" currently buys nothing. The ruling preserves 40 days of history that no served surface can reach. The value of the ruling is unrealised until a reader can ask for a time range instead of a byte count.

Why a byte tail, and what replaces it

The byte tail is a correct answer to a real problem — an unbounded read of a 1.7 GB file on the request path would block the event loop, which is the failure class already firing nightly. The replacement is not "read more"; it is read by time, from an index: a periodically-built offset index (day → byte offset) so a reader seeks to the start of its window and scans forward, keeping the per-request cost bounded by the window rather than by the file. Until that exists, every spine-derived metric should state the window it actually covers.

Writers

Three adapters, one shape

bash emits via chorus-log <event> <role> k=v…; TypeScript via the SpineEmitter closure over Pino; Rust via the chorus-hooks daemon. Raw echo, println!, and console.log are forbidden for spine events — the adapter is what guarantees the envelope. Full adapter contracts live in logs-service-design.html.

Gap 3 — there is a second spine, and nothing reads it. platform/chorus-sdk/src/emit.ts resolves LOG_FILE to platform/logs/chorus.log, while every reader listed above reads ~/.chorus/chorus.log. The SDK file exists, is 106 KB, and holds 485 events across 4 distinct types (mostly session.context.built), most recently at 03:50 today. Anything emitted through the SDK is written correctly, validated correctly, and invisible to every consumer. This is the single most consequential defect this design surfaces: guarantee (1), one log, does not hold today.

The spine and MCP — one surface, two faces

Jeff's framing, this morning: "mcp is ~ spine at its core tho all products are visible via it." Stated precisely:

  • MCP is the door — the typed, governed entry point for every action an agent can take.
  • The spine is the record — what came through the door, in order, with its trace.

If that duality holds, then the tool list and the event registry describe the same system from opposite ends, and each should be derivable from the other. Today they are authored independently: ~57 tool definitions hand-maintained in platform/mcp-server/src/server.ts, 345 event types hand-maintained in spine-events.json, with no check that a tool leaves an event or that an event has a door.

The test this design proposes. For every MCP tool, name the spine event it emits; for every event whose vertebra implies an action, name the tool that produces it. Both directions produce a list of holes, and the size of those lists is the honest measure of "all products are visible via MCP" — a claim we currently assert and never check.

As-Is — 2026-09-01

  • Retention ruling honoured: 1.71 GB, never rotated, 40 days retained.
  • Registry healthy: 345 types, each with vertebra, keys, and field docs.
  • Writer normalisation good: three adapters, one envelope, enforced by review and by the emit gate.
  • Reach broken: 0.25% of the record is served; range controls over spine data are decorative.
  • Log unity broken: an SDK-written second file that no consumer reads.
  • MCP↔spine correspondence: asserted, never verified.

Path to close

  1. One log. Point chorus-sdk's LOG_FILE at the same path every reader uses (CHORUS_LOG, defaulting to ~/.chorus/chorus.log), and add a check that fails when two spine paths are writable — with a fixture proving it fails, per the negative-proof rule (#3734).
  2. Read by time. Build the day→offset index; give the spine readers a since parameter; make the Team Pulse range buttons mean what they say. Until then, every spine-derived number states its true window.
  3. Correspondence check. Emit the tool↔event mapping as data and report both hole lists. This is the mechanical form of Jeff's claim.
  4. Register this doc in the doc catalog under Architecture & Design, and cross-link it from chorus-spine.html and logs-service-design.html with the two-senses note.
