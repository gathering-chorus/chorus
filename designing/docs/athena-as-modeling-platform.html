Athena as a Modeling Platform — vision & context

Wren · 2026-07-31 · a summary of Jeff's framing in session, captured so #3706 is built against the vision rather than against a page request. Not a design doc — the design lives in athena-product-design.html; this records why and where it goes.

1 · The frame Jeff drew

A product — Gathering, Chorus, or something new we build for a customer — has:
  • a model (the OWL)
  • an OWL generator (owl-api)
  • a way to observe the graph as a function of the OWL
  • views over its value streams, products, domains, services, and domain instances

That makes Athena a product template, not a one-off. The generator is shared; the model is per-product. It also reframes what Chorus is: not internal infrastructure, but a method plus the tooling to run it.

2 · The consultant workflow

"So Athena allows me as a consultant to start with customer — define a small value stream quickly — define associated domains for the value stream quickly — same for services and products — see the whole OWL model filterable by VS, domain, product, service … then we can generate APIs from the model."

model the customer's value stream   →   athena-model    (#3718, to build)
        ↓
generate their APIs                →   owl-api         WORKS TODAY
        ↓
see it, filterable                 →   model view      (#3706, in flight)

The deliverable at the end of a modeling session is a queryable system, not a slide deck. That is the differentiating claim, and the API-generation leg of it is not speculative — see §4.

4 · What already works

  • API generation from the model. All 21 collections above are generated — no hand-written routes. The last leg of the consultant loop is the one that already runs.
  • A governed writer, for instances. platform/services/chorus-model (Rust, #3257): add / mint, callers never pass IRIs, --dry-run prints the Turtle. This is the deterministic core — it just stops at the ABox.
  • The Service layer opened. chorus:service-clearing is the first Service instance in the graph (#3675); the Clearing service design now derives from it and states the rule that should govern every page: "The model is the source of truth; this page is its narrative view and must not contradict it."
  • The Gathering value stream exists as of 2026-07-31 — seven steps (Sowing · Growing · Practicing · Tending · Harvesting · Reflecting · Connecting), authored on #3706. It is the first non-Chorus stream in the model.

5 · The gaps that matter, in order

ONE MODEL, NOT N. Single chorus: namespace, single ontology graph, single MODEL_SET. A consultant needs one model per customer, isolated. This primitive does not exist — and it is the same defect that has /products returning 0 today: one ontology serving both Chorus and Gathering, so "which product owns this class" has no answer. athena-product-design.html already ruled the split ("Gathering's data domains belong to Gathering's ontology") and it was never executed.
THE SCHEMA LAYER IS UNGOVERNED. Classes, properties and shapes are hand-typed into .ttl. Consequences measured 2026-07-30: 186 classes across 13 files and 6 namespaces; 69 classes (38%) declare themselves and bind nothing (outside MODEL_SET); 11 properties with no rdfs:domain and/or rdfs:range; 12 classes with no SHACL shape, which owl-api refuses to serve; DomainShape and the ontology disagreeing about what a Domain is (8 attributes each, only 4 overlapping). #3718 is the fix: extend the governed writer to the TBox and close the hand-edit back door.
THE GENERATOR EMITS APIs, NOT PAGES. 21 collections, 5 pages. A customer sees JSON unless someone hand-writes HTML — and hand-written pages are how we got fifteen competing "show me the model" surfaces.

6 · Rulings taken in this discussion

  • Absence is never canonical. Born-v2 removed (2026-07-30, Jeff): an untagged class is unclassified — nobody has reviewed it — not v2. Reviewed classes carry target or legacy. Removed from both the ontology and owl-api; proven on a running binary.
  • The shape is the source of truth (Silas, OWL-DBA): rdfs:domain infers rather than constrains, and we run no reasoner, so those declarations do nothing operationally. SHACL is what refuses. rdfs:domain/range derive from the shape, never hand-maintained beside it — with the caveat that shape edits are therefore model edits, validated against live instance conformance before deploy.
  • The API serves the target model; the ledger watches the dying one (Silas): a class mid-retirement does not get a shape to make it observable — that expands the surface of something we are removing. Retirement is measured by SPARQL, not served.
  • Retiring things are not structure. Do not cite a class we are retiring as if it were core. Legacy is filtered out of the model view by default.
  • Sequence is already set by athena-product-design.html: "Service type-migration first (smaller, isolated), then recursive-Domain collapse." The SubDomain retirement is the recursive-Domain collapse — step two, gated on the Service migration. Not a drive-by edit.

7 · The open question

Is the pitch speed or legibility? "Define a value stream quickly" and "the customer can see and trust it" pull the tooling in opposite directions — one wants defaults and inference, the other wants refusals and honest gaps. Two days of evidence say inference invents judgments nobody made (born-v2 stamped ~120 unreviewed classes canonical). Unresolved, and it decides how athena-model behaves when a field is missing.

8 · Recommended next move

Make Gathering the pilot customer. Not as cleanup — as the proof. Stand Gathering up as an independent model with its own namespace, value stream (now authored), domains, services and product. If that works, "model a customer's value stream quickly" has been demonstrated once, on a real subject, before anyone pays for it. It also fixes /products=0 as a side effect, because a second real model is what makes the product axis mean anything.
