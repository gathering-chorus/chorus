Role as Living Configuration

Today a role is a markdown file we regenerate. The evolution: a role becomes a graph entity whose behavior is readable, tunable, and observable while it runs — and the markdown becomes one projection of it.

Wren · 2026-08-06 · born from Jeff: "we might have both global and role level rules that drive behavior" → "properties that tune role dialog" → "shared config that is read by the role and changeable"

The one-sentence target

GET /roles/wren answers: who holds this role, what it's for, what rules govern it, how it's tuned right now, and what changed lately — one query, live.
Today that answer is scattered across a CLAUDE.md, a fragments directory, a memory file, and Jeff's patience.

Five layers, one entity

The design separates what changes at different speeds. Identity almost never changes. Charter changes when the team changes shape. Rules change when we learn something. Tuning changes mid-conversation. Observation never stops.

The three design calls

Scope is an axis, not a subclass. One Rule shape with scope: global | role (role-scoped rules carry a Role edge). Same call as principalKind and principleKind — one collection, one enumerable list, shape constraints per scope value. Four subclasses would mount four API surfaces and split the "what governs Wren" answer.

Precedence is written, not emergent. Live Property > role Rule > global Rule — and a Property may only tune within what rules allow (a knob can set dialog.verbosity=terse; it cannot switch off "the ask survives 2-3 scans"). Conflicts refuse at the pen, not at read time.

Two consumers, one graph. The generator (build-time → CLAUDE.md) and the boot/context-inject (run-time → session envelope) read the same instances. What a session actually received is already on the spine (context.inject.* events), which makes conformance measurable instead of vibes: DECLARED (graph) ⊇ COMPOSED (CLAUDE.md) ⊇ INJECTED (session) — three sets, checked, the discipline that caught this week's serving bugs.

Strangler path — five steps, nothing breaks

1. Facts first: import existing fragments as Rule instances (byte-faithful, like the principles migration). Files still drive; graph mirrors.
2. Drift check: generator verifies manifest == graph on every compose — a fragment on disk absent from the graph fails loudly (the #3764 negative proof). Behavior unchanged.
3. Inversion: generator derives FROM the graph; files become committed projections (same pattern as owl-api generated surfaces landing in the repo).
4. Knobs: register the first dialog PropertyKeys; boot envelope + context-inject read them live; Jeff changes one and sees the next turn obey.
5. Reflection: Borg fitness rows per role over the spine. The loop closes: he tunes, the system measures, drift surfaces as data.

What this is NOT

Not a rewrite of the fragment system — it worked for six months and its compose discipline survives as step 3's generator. Not per-turn prompt assembly from the graph — the durable floor stays a committed file (reproducible, reviewable); only the knobs are live. Not a new domain — it's the roles domain finally getting the treatment principles got this week.
