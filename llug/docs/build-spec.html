The model

Source of truth

OWL classes and SHACL shapes for the seven domains, in the repo, deployed to its own urn:llug: graphs.

Everything downstream is generated from this file. Change the model, regenerate — do not hand-edit what came out.

The llug API

Generated

Read and write routes per class, from the shapes. Same generator that already serves Chorus's own domains.

Owns the writes: the phone never talks to the graph or to a plant service directly.

The field app

Hand-built — the only one

A PWA. Camera, a two-way toggle, a checklist, a queue. No thinking, no keyboard, no network required.

Small on purpose: if this stays small it stays reliable, and reliability outdoors is the whole product.

Installed to the home screen, and the queue drains when it is open — iOS gives no background upload, so the app never promises one.

shared-security

Reused, not rebuilt

Sign-in and permissions come from the team's existing identity service — the same one Chorus uses. The garden app writes no auth code of its own.

Second consumer, so it is also the first real test of that service outside Chorus. Silas owns it.

The renderer

Already working

HTML in the Light Life brand, printed to PDF headless — exactly how this morning's proposal and plates were made.

The client document and the internal plates are one template with two audiences.

Six · four outdoors, two at the desk

The interface is part of the spec, not a separate document — the engineering picks above only make sense next to what they are in service of. Four of these are used standing in a garden with dirty hands; two are used sitting down.

The camera is the home screen

Open the app and you are already shooting. The only decision is the toggle above the shutter, and it is a thumb's reach from where the hand already sits.

Screen 03 · Identify

The machine guesses, you confirm, both are kept

Ranked candidates with real confidence numbers, and the local judgement on top — the one thing a general plant app will never tell you, because it does not know which state you are standing in.

"Not sure" is a first-class answer. It queues the plant for a closer photo instead of forcing a name, and an unconfirmed identification never becomes a fact.

Model behind it

Identification keeps candidate, score and source, and is never overwritten. Planting.ofPlant records only what you confirmed. JurisdictionStatus supplies the red line from the state's own published list.

Engineering picks

And how hard each is to undo

PickWhyReversible?
PWA, not native iOS One codebase, no App Store review, no developer account, and camera plus offline storage are both fine in a modern browser. There is one user in v1. Go native only if background sync or camera control proves genuinely inadequate. easy
IndexedDB queue Photos and observations land locally first, always. Sync is a separate step that can fail without losing anything. easy
Drains when open, not in the background Kade, 2026-09-07: Safari has never shipped Background Sync. Nothing uploads while the app is closed. So the queue drains on reopen, and the count of waiting items is visible on screen — a promise the app can actually keep. easy
Add to home screen, required A plain Safari tab loses its storage after about seven days of not being used. Installed, it keeps it. This is a setup instruction, not a preference. easy
One photo per request Never one batch. A failed upload costs one photo and retries by itself; a failed batch of forty costs a day in the garden. easy
ID key server-side An API key on a phone is a key you have given away. A broker also lets the provider be swapped after the probe without touching the app. easy
Fuseki + generated API The same path Chorus already runs. It is the reason the model can generate anything at all. hard
Its own urn:llug: namespace A second product in the same store must not share graphs with Chorus. This is the boundary that keeps the test honest. hard
shared-security for sign-in Jeff's rule, and the right one. A one-user garden app that invents its own login is how a second auth system is born. It also means a client link can later be given real permissions rather than a shared secret. hard
HTML → headless PDF Proven this morning. No document library, no template engine, and the same CSS makes the web page and the printed sheet. easy
Runs on the mini Where everything else already runs. The phone reaches it over the LAN, and over the internet later if a client ever needs a link. easy

The two hard-to-undo picks are the two that make the thesis testable. If the generated API cannot carry a second product, we want to find that out on a garden app with one user — not later, on something that matters.

Order of build

Each stage usable on its own

  1. The model in the repo. Seven domains, sixteen classes, shapes. Nothing runs yet; everything else depends on this existing.
  2. Generate the API and deploy the graphs, behind shared-security. First honest answer to whether the generator — and the identity service — carry a second product. If they do not, we learn it here, cheaply.
  3. The renderer against real rows. Anthe's proposal, generated from work items instead of hand-written. A page a client already received is the test.
  4. The ID probe. One photo, one call, one verdict — and whether the names match the Massachusetts list at all.
  5. The field app, capture only. Camera, toggle, queue, sync. Nothing else. Used in Jeff's own garden while there is still a season.
  6. Plates assembled from captured rows. The evening screen. The loop closes and the paper prototype retires.

Stages 1 to 4 need no phone app at all, and stage 3 produces something a client can hold. If the survey stops after stage 4, the business is still better off than it was this morning.
